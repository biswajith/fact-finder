Many documents, one bid

The extractor reads one RFP. A real bid also has addenda, call transcripts and the team's own deal notes. This page proposes how each kind of document is read, and how the facts from all of them agree on which one to believe. Every step is marked by who does it: the model, code, or the user.

Terms used on this page
  • Unit: one sentence, list item, table row or heading, cut by code and given an ID such as p3.12. The model sees units; it never makes them.
  • Label: the model's closed answer for a unit: a category code, = (continues the point of a unit just before) or - (states no point).
  • Fact: a coded unit plus the continuation units after it. Its ID is a hash of the document ID and the coded unit's ID (units.fact_id), so it does not change with the code, the wording or the run.
  • Group: GROUP's answer that some facts state the same point or are items of one list. Today groups change how facts are shown, never which facts exist.
  • Level: where a source sits on the priority ladder, 1 (buyer documents) to 4 (deal notes). "Authority" is the property that sets it.
  • Relation: a link from a unit in a later document to units in an earlier one, of a fixed kind: replaces, removes, adds, clarifies, confirms, disagrees or none. Relations never rewrite a fact's text.
  • Subject test: whether two facts that give different values are about the same thing (the same event, item or term). Defined in Duplicates across documents.
  • Q fact: a contradiction inside the buyer's own material, kept in the fact list. Today it is always inside one document (CHECK and XREF).
  • Conflict: a decision card in the workspace that asks the user to choose between options. Today a Q fact shows as one, and the chat or the fact check can raise one (Workspace.raise_conflict).

1. A document becomes units

CLASSIFY proposes a type and the user confirms it; the cutter for that form cuts the units. A transcript also gets a speaker map that the user confirms. Other forms go straight from the cutter to the units.

  • AD QA Confirm: addenda are also put in issue order (number, then date), and the user confirms any order of precedence the buyer states.
  • AT Cut into units: spreadsheet or PDF cutter for a pricing workbook, forms or sample contract.
  • TR Cut into units: sentences inside speaker turns, with the speaker stored on each unit; then the speaker map and its confirmation, which only transcripts have.
  • DN Cut into units: notes cutter: entries and their lines.

2. Units become facts and links

The label round answers about every unit, and code builds the facts and sets their levels. RELATE links the units of a change or context document to earlier units, and code applies those links with the ladder. GROUP finds repeated points across the bid; code keeps same values as one point and hands on every pair whose values differ, with the facts that still state an old value.

  • AD Label round: as for an RFP, but a section reference is held back until RELATE answers.
  • TR Label round: the transcript playbook: its own categories, a tentative flag, the question-and-answer rule.
  • DN Label round: the notes playbook.
  • TR DN Build facts: level 2 for buyer units and 3 for ours, from the speakers of a fact's units; deal notes are level 4. Buyer documents are level 1.
  • AD QA RELATE: every unit, against earlier buyer units and headings: replaces, removes, adds; a Q&A answer mostly clarifies or adds.
  • TR DN RELATE: against buyer documents: confirms, clarifies, disagrees, adds. An RFP and an attachment skip RELATE: they are the base.
  • RE Apply relations: a reissue has no RELATE: it is aligned with the previous version by text, and corrections move to the new fact IDs.

3. Disagreements are settled, and the outputs made

The pair check, the ladder and the user's decisions settle what disagrees; the decisions go into the correction log. The stored facts and relations, applied in issue order with the log replayed over them, give the bid's fact list, its summaries and the exports.

  • AD Apply the ladder: between buyer documents the later issue wins, unless a stated order of precedence says otherwise.
  • AT Apply the ladder: an attachment issued with the RFP has no order against it, so a disagreement is a Q fact, not a replacement.
  • TR DN Exports: internal by default, so their citations are left out of anything sent outside the team.

All documents of one bid sit together in a bid: an ordered list with each document's properties and issue date. Unit IDs stay as they are; a citation is a pair, (document, unit), shown as d2 · p1.4, where d2 is the document's number in the bid. Today a citation holds no document (Anchor.citation()), so every place that compares citations by unit ID must compare the pair.

Unit IDs should not be prefixed with the document. fact_id already hashes the document ID, so IDs are unique across a bid as long as document IDs are; a prefix would change every fact ID and cut existing correction logs, labels and reference lists loose from their facts. What the bid must enforce is unique document IDs, since today they default to the file name. Only inside a RELATE prompt, where units of two documents appear together, does code write the pair as one token (d1:p2.31); it maps the token back before anything is stored.

Playbooks

Each document type gets a playbook: the standing rules for reading that kind of document, chosen the way a skill is chosen. Today the RFP's playbook exists but is spread across the code: units.SYSTEM, the task texts, prompts.DEFINITIONS and PRECEDENCE, units.CODES and MODEL_FLAGS, modal_flags and SECTIONS. goldset reads a second copy of the fact rules and flag tests from prompts.SYSTEM (golden.py).

A playbook configures the pipeline; it is not one prompt. Its header is read by code; its body becomes blocks of the system prompt that the model reads.

---
name: call-transcript
description: Recording or notes of a live call between buyer and bidder;
  speaker turns, timestamps, conversational wording.
cutter: transcript             # sentences inside speaker turns
codes: [D, C, R, E, PRIORITY, DECIDER, BUDGET, QUESTION]
flags: [post-award, risk, unclear, tentative]
calls: [LABEL, STATE, RELATE]
relations: [CONFIRMS, CLARIFIES, DISAGREES, ADDS, NONE]
votes: 3
level: by speaker              # buyer units 2, our units 3
relate_to: buyer documents
visibility: internal           # default for citations from this document
sections: [buyer-priorities, open-questions]
version: 1
---

- A question states no point by itself. When the answer only agrees or disagrees,
  label the question with the point and the answer as its continuation. When the

- A hedged statement is still a point; flag it tentative.

Priority ladder

Buyer material is the most authoritative and deal notes the least. In a transcript, the side that said something decides its level.

1
Buyer documentsRFP, addenda, attachments. The order of precedence the buyer states decides when the RFP has one and the user has confirmed it; otherwise the later issue wins. Documents issued together, such as the RFP and its sample contract, have no order: a disagreement between them is a Q fact.
2
Buyer on a callA clarification, answer or hint from the buyer's side. Not binding until a buyer document confirms it.
3
Our side on a callWhat our team said, assumed or promised.
4
Deal notesOur own view: intelligence, guesses, to-dos.

Code The rule: a fact from a lower level never changes a fact from a higher level, and below level 1 nothing replaces anything automatically: two disagreeing statements at levels 2 to 4 are both kept and shown to the user.

User The one exception is the user. When resolving a conflict, the user may choose to rely on a lower source, for example a verbal clarification. That choice is logged as theirs.

When a lower level touches an existing fact, there are three outcomes:

  • Confirms it. A relation is recorded. The higher-level fact keeps its text.
  • Adds something new. It is a fact at its own level, cited to its source.
  • Disagrees. What happens depends on the two levels, below.

When sources disagree

Disagreements are found in three places: CHECK inside one document Model, RELATE between documents Model, and the group check across the bid, where code lists pairs whose values differ Code and the pair check says whether they are about the same thing Model. Code applies the outcome below; a conflict goes to the user User.

"New" means later by the document's issue date or call date, not later uploaded: a document uploaded out of order is treated as if it had arrived in date order. Pick the two sides:

Conflicts use Workspace.raise_conflict, which already takes options that each carry their changes (edits and deletes of facts; an option may carry none). Three things are new: a conflict raised for a document, since today only the chat and the screen can raise one; an option that records a question for the buyer; and closing a conflict automatically when a later buyer document settles it. "Marked replaced" on this page always means today's replaced flag, plus a relation that names what replaced the fact.

Duplicates across documents

The same fact turns up in several places: the due date in the RFP, in Addendum 1 and on the pre-bid call. Nothing merges facts today. GROUP links facts of one category that state the same point, or are items of one list, and apply_groups turns a "same" group whose numbers and dates differ into a list titled "Related statements". That split is the one this design needs, so GROUP run over the whole bid is the mechanism.

Same subject, and…Result
the same values (numbers, dates and times, as normalize.values reads them)Same group Shown as one point with every citation, each with its document and level. The text shown is the highest level's current fact (today: the first fact in document order).
different valuesNot a duplicate Shown as related. A pair from two documents goes to the pair check; if it confirms they give different values for the same thing, the ladder decides.
one side adds detailRelated Both stay as facts of their own.
  • Code Facts are never merged in storage. A group links them, so no merge or split is needed; the user can ungroup a wrong group (a new log operation).
  • Code Group IDs hash the bid, not one document, and each line GROUP reads names its document, since page numbers repeat across documents.
  • GROUP works per category. A due date stated as a D fact, an X fact and an S fact is not grouped together, and those are not duplicates. What matters is that all three are found when the date changes; the subject test does that.
  • Code compares only numbers, dates and times. A "same" group of facts that hold none passes the check on the model's word alone.

Code Model The subject test

Whether two facts that give different values are about the same thing. Two facts with the same values are GROUP's business; this test is only asked about pairs whose values differ. It is built from what exists:

  1. Code List the pairs: two facts of one "same" group from GROUP whose values differ; a new fact and the facts that hold a value it replaced (normalize.values); and a new fact and the top of the search ranking the workspace uses for related facts (agent.related_facts, 8 facts today).
  2. Model Judge each pair with the fact check that already exists: "do these give different values or rules for the same thing?" (web/consistency.py, threshold 0.7). It answers no when the two are about different things, when they agree, and when one only adds detail.
  3. Code Apply the ladder's outcome at or above the threshold, and send pairs just under it to review. The review band is new and has to be set by measurement.

Today a fact check that fails, or has no API key, is skipped and the fact stays. For a document that is not good enough: a pair check that did not run is recorded on the document and run again.

Lean towards not grouping. A wrong "same" hides a real change, which is worse than a duplicate line. apply_groups already refuses a "same" group whose values differ; keep that rule at the bid level, and show close pairs as related, not same.

Visibility belongs to each citation. A fact can be exported when at least one of its citations may be exported, and the export shows only those citations. A buyer fact that a deal note also mentions stays exportable; the note's citation is hidden.

Addenda

An addendum is labelled like any other document. Its units become facts of their own, cited to the addendum. A change is a relation from an addendum unit to the base units it changes; code marks the base facts replaced. RELATE answers for every unit of the addendum, not only for its facts, because the sentence that carries the change ("Section 3.17 is deleted") may itself be labelled -. A base fact's text is never rewritten, because a fact's text must be the source's own words, or a statement whose numbers are in its units.

CodeModel answers, code checksShown to the user

Code User 1. Put the addenda in order

  • Addenda apply in issue order: addendum number, then date. CLASSIFY reads them; the user confirms on upload. Upload order doesn't count.
  • The buyer's order of precedence comes first. A clause such as "in case of conflict, addenda govern, then the RFP, then attachments" is labelled as a fact like any other, but code cannot read a ranking out of a sentence. The buyer-document playbook gives such a unit a voted precedence flag Model; the user reads the flagged fact and sets the order of the bid's documents User; code applies it. Until then the later issue wins.
  • Relations are applied in issue order, not in the order the documents were loaded, so Addendum 3 loaded before Addendum 2 still applies after it. See the correction log.

Model Code 2. Find what each unit may point at

Code gathers candidates; RELATE picks among them. Code does not resolve a reference by itself: matching "Section 3.15" to a heading by its words was tried for XREF and found one of nine real mistakes on the two test RFPs (xref.py), because most headings and references have no fixed shape.

  • XREF runs on the addendum and finds its references; code keeps a reference only when its text is in the unit, as today. For a unit with a section reference, the candidates are the headings of the earlier documents, which is a short list.
  • Today XREF only points at units of its own document, and reports a section reference with no target as a problem. On a change document that would turn every "Section 3.15 of the RFP" into a false Q fact, so such a reference is held back until RELATE has answered.
  • A unit with no reference ("the due date is extended to…") gets candidates from code: earlier facts that share a number or date with it (normalize.values), and the top of the workspace's search ranking for its text (agent.related_facts).
  • When RELATE finds no target for a reference among the earlier documents' headings, the reference is shown as a Q fact and nothing is applied.

RELATE reads a batch of addendum units with the candidates for each and gives one closed answer per unit, in the same shape as LABEL:

The kinds are REPLACES, REMOVES, ADDS, CLARIFIES, CONFIRMS, DISAGREES and NONE; a playbook lists the ones its documents may use. Code checks that every target was among the candidates it showed, and asks once more for units left out, as LABEL does. The answers are stored with the document's result, like labels.json, so they are not asked for again.

A target may be a unit labelled -, since labels.json keeps every unit, or a heading. A heading stands for the units from it to the next heading, in document order: headings have no levels today, so a section with subsections is named by listing each of its headings, and the playbook says so. Code shows the user the facts a heading reaches before it marks them.

Code Model 4. Apply: one change, several facts

The addendum names one place, but the old value may be stated in several. Code lists the other facts that hold a number or date the replaced fact had and the new fact does not; the pair check says which of them are about the same thing (the subject test). Code flags those; it does not rewrite them. Each flag is a conflict whose options carry the edit ("update to June 24"), so the change is the user's, made with one click, and goes through the log like any edit.

Code Model Reissued full RFPs

A reissue has no list of changes. Code first aligns units by text with the previous version, in order, so that repeated text pairs up in sequence. Aligned units keep their votes and labels. A fact is carried over, with the user's corrections, when every one of its units aligns; a stored map from old fact ID to new keeps the log pointing at it. Units that don't align are labelled, together with any continuation whose coded unit changed, and they are reported as changed, new or removed. CHECK and XREF read the whole document, so they run again on the new version. The previous version's facts then leave the current list: a carried fact continues as its counterpart, and the rest are marked replaced.

Comparing two extracted fact lists instead would report false changes, because labels differ on about one unit in ten between runs. If the buyer issues both a change list and a reissue, a difference between them is a Q fact.

The Durham test file named "Addendum 1" is a reissued full RFP, not a change list. A real change or Q&A addendum is needed to test RELATE.

Who is speaking

The ladder only works if every transcript unit is on the right side. A wrong side turns our own guess into a conflict against the RFP.

  1. Code Units are sentences inside a turn. The turn plays the part of a page; the speaker is stored on the unit. Anchor has no speaker field today, so one is added (the section field is the stopgap).
  2. Code Speaker names are matched by exact name to a team list the user keeps for the bid (new), and to names that appear in the bid's B facts. Code proposes a side; it does not decide one.
  3. User The speaker map is confirmed once per transcript, before labelling: the proposed sides are shown and unmatched speakers are named.
  4. Model Code A fact can span both sides. If we ask "so the deadline is the 24th?" and the buyer answers "yes", LABEL codes our question and marks the answer as a continuation, so the fact starts on our side. Code sets the level from the speakers of all the fact's units: a fact with a buyer unit gets the buyer's level and a both sides mark. Code cannot tell whether the answer agreed, so such a fact is shown in the source's words with both turns, never as a STATE statement (today the statement is written for the coded unit alone, here the question). The higher level is the safe choice: at level 2 a disagreement with a buyer document is a conflict the user sees, and nothing is replaced. A buyer answer that states a point of its own ("no, the 30th") is a coded unit and a fact of its own.
  5. Model Hedged statements get a voted tentative flag from the transcript playbook. A tentative buyer statement that disagrees with the RFP is still a conflict, and the card shows the flag.

Changes to the correction log

Addenda, reissues, transcripts and notes all reach the user's facts through the correction log, so its changes are shared by every document type.

Today _entry accepts only the sources chat and ui; the operations are edit, delete, add, raise, resolve and undo; and replay applies the live entries in file order over one run's facts. Some of that order carries meaning: a change made by resolving a conflict belongs to the resolve entry written just before it. So entries cannot be re-sorted by issue date.

Proposed: relations are not log entries. They are stored with each document's result and applied in issue order to build the bid's facts, and the user's log is then replayed on top in file order, as today. The log gains two operations, reject a relation and ungroup, and a conflict that code raises for a document is derived from the relations, the way a Q fact's conflict is derived from the facts today. Its ID is fixed, so the user's choice stays attached to it, and it closes when a later buyer document settles it. A conflict the user had already resolved is not changed silently: it is shown again with the new document.

Build order

  1. RFP playbook, no behaviour change. Gather today's pieces into the playbook shape. Test: the assembled system prompt and task texts are byte-identical to today's, so the cache key and VERSION don't change. (A score comparison is not a usable test: labels vary between runs.)
  2. Bid, CLASSIFY and citations. Group documents with their three properties; CLASSIFY and the user's confirmation; unique document IDs; (document, unit) citations wherever citations are compared; playbook name and version in the stored-result key.
  3. Relations under the correction log. Relations stored per document and applied in issue order before the log is replayed; reject-relation and ungroup operations; documents as a source of conflicts; conflicts that a later buyer document closes.
  4. Priority ladder and visibility in code. Levels on facts and citations; the disagreement outcomes, which need the conflicts of step 3; exports filtered by visibility.
  5. GROUP across the bid and the subject test. Group IDs hash the bid; groups show their highest current member; the pair check runs on pairs code lists; the ladder of step 4 decides.
  6. Change-addendum playbook and RELATE. Uses the candidates and the pair check of step 5. Needs a real change or Q&A addendum to test on.
  7. Reissue alignment. Units aligned by text; corrections carried to new fact IDs.
