Chat planning: what we measured and what to change

Today the chat treats "make a plan" and "ask the customer first" as one thing, and a router guesses which messages get it. The measurements say they are two things. The plan is what makes the agent accurate. Asking is a separate choice.

2026-11-25. Numbers from runs/_chateval/full-3x and runs/_chateval/plan-no-approval-3x; run them again with fact-extractor chat-eval evals/chat/durham.yaml --repeat 3.

How it works today

A router reads the customer's message and picks a mode before anything is looked up:

  • Direct: no plan. The agent acts one step at a time.
  • Light: the agent writes a short plan from the message alone, without looking anything up.
  • Heavy: the agent first looks things up without changing anything, then writes a plan that names the facts.
  • Auto (the default): the router picks one of the three for each message.

By default a light or heavy plan also stops and waits for "yes". So a message either gets no plan at all, or a plan and a stop. There is no "plan, then get on with it".

What the numbers say

  • The plan is what helps, not the stop. Heavy with the stop turned off passed 68 of 75 in one message per case. With the stop it passed 67 and needed two messages.
  • The plan has to come after a first look. A plan written from the message alone (light) is the weakest setup, with or without the stop.
  • Planning every message is cheap. On a simple lookup it adds about two seconds and two model calls over no plan.
  • No plan is risky on changes. Direct rewrote facts from the call or our notes in 5 of 6 runs, and picked a side in a conflict nobody had chosen in 3 of 3.
  • The stop earns its place in a few spots. Without it, ambiguous messages dropped from 6 of 6 to 4 of 6, and one record case slipped.
  • The router adds nothing. Auto is the worst overall: it sent every record case to direct, where nothing guards them.
  • One bug is separate from all of this. Told which side of a conflict to take, heavy rewrites the fact and leaves the conflict open.
How far to trust this: three runs per case is few, and single cases swing between runs. The pretend customer approves every plan without reading it. The 25 messages are on one bid.

The change: every message gets a plan

One path for every message, and no router. The agent reads the request, takes a first look with the tools that only read, writes a plan the customer can read, and carries it out. For a simple question the plan is one line.

1. LookThe agent searches and reads what the request touches. Nothing can be changed yet.
→
2. PlanIt writes the steps in plain words, naming the facts, and lists every change it intends to make. The customer sees it as a card.
→
3. Carry outCode holds the agent to the plan: a change the plan did not list is refused.

If the first look shows the message could mean different facts, the agent asks a question instead of writing a plan. That exists today and stays.

Asking first is a separate setting

Whether the agent stops between step 2 and step 3 is a choice about trust, not about planning. Because the plan lists its changes, code can decide from the plan itself. The setting has three values:

SettingThe agent stops for "yes" whenWhat the measurements suggest
NeverNever. The plan is shown and carried out.68 of 75, one message. Weakest on ambiguous messages.
When it matters (proposed default)The plan would change a fact from a call or our notes, change more than one fact, or resolve a conflict.Not measured yet. Should keep one message for questions, added facts and single corrections.
AlwaysEvery plan.67 of 75, two messages for everything, including questions.

Which changes count as "it matters" is the debatable part. The three listed are where the runs went wrong; the list is one place in the code and easy to change.

What goes away

  • The router and its model call on every message.
  • Direct mode and light mode, and their prompts.
  • The rule that approval depends on the mode.

Steps

  1. Have the plan list its changes (which facts it will edit or delete, which conflicts it will resolve), and refuse any change it did not list. Today this check covers only facts from a call or our notes.
  2. Add the "when it matters" setting, decided from the listed changes.
  3. Fix the conflict bug: an edit to a fact in an open conflict is refused, and the agent is pointed to resolving the conflict.
  4. Add three or four more test messages each for records, conflicts and ambiguous requests, and run each case five times.
  5. Compare the new path at all three settings against today's modes.
  6. If it wins, make it the only path and remove the router, direct and light.

Done means

  • With "when it matters", the new path passes more cases than any setup in the table above (best today: 68 of 75).
  • It passes every record, conflict and ambiguous case.
  • Questions, added facts and single corrections take one message.
