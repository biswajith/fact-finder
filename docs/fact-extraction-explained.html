How the fact extraction phase works

An RFP is a long document a buyer publishes to ask companies to bid. This phase reads one RFP and produces a list of cited facts for the bid manager: what is due when, what disqualifies a bid, what the package must hold. The model never writes that list. It answers one fixed question per sentence, and code builds the facts from its answers.

The nine categories, and two other answers

For each unit the model answers with one of eight category codes, or with = or - (see the second table). Q is the ninth category and is found separately. Every fact has exactly one category. Examples are made up. When a point fits several, the first in this order wins: X, G, D, S, E, C, R, B.

Worked example

Six units from a made-up RFP. Each unit has three votes. Change any vote or any sentence and the winning label and the facts update using the same rules as the real code. Try making a vote split three ways, or turning a = into a -.

Facts built by code

In a real run the fact text is the model's one-line statement (kept only if its numbers match the source). Here the fact shows the source words so you can see what was joined.

Majority vote

The label most of the three runs gave wins. A split is kept on the fact as 2/3.

No majority

The category earliest in X, G, D, S, E, C, R, B wins, because a missed fact costs more than an extra one.

Continuation reach

A = joins the previous fact only if it is within 3 units of the last unit attached to it.

Flags from wording

For R, S, G, C and X, "must", "shall", "will not be opened" give mandatory; "should", "preferred" give desirable.

1. Cut the document into units

Done before any model call, by code, the same way every time. A sentence, a heading, a list item and a table row each become a unit with an ID: p3.2 is page 3, sentence 2; p3.t1r3 would be page 3, table 1, row 3. A sentence over 60 words is split. The result is the tagged text above, and every model call gets the whole document in this form. The units are also grouped by whole pages into chunks, which step 2 explains.

Why: the set of possible facts, and each fact's identity, must not depend on the model.

2. Send one round of calls at once

Every call starts with the same system prompt and the whole tagged RFP, so the provider can cache it. The first call goes alone until it starts streaming (at most 10 seconds), then the rest are released together. Each call adds only a short task message.

Every call reads the whole RFP, so the model always has the surrounding context. What differs is how much of it the call is asked about:

CallReadsAsked aboutRuns
LABELWhole RFPOne chunk of about 60 units (whole pages)3 times, once per vote, for every chunk
STATEWhole RFPOne chunk of about 40 units (whole pages)Once for every chunk
CHECKWhole RFPThe whole document at once, no chunksOnce

Example: an RFP cut into about 600 units gives roughly 10 label chunks and 15 state chunks. That is 10 × 3 = 30 LABEL calls, 15 STATE calls and 1 CHECK call, so about 46 calls, all started together. Chunks follow page boundaries, so the sizes are approximate.

Why chunks for LABEL and STATE: each unit needs one output line, so a long document in one call would hit the output limit and run slowly. Why no chunks for CHECK: a contradiction compares two places that may be far apart, so the call must look at everything at once.

Why three kinds of call: labelling, wording and contradiction-hunting are separate questions. Mixing them lets one answer bend another.

3. Vote

Code reads the three label answers and picks a winner for each unit. Most units are unanimous. The interesting ones are splits.

UnitVotesWinnerWhy
p3.2D, D, DDAll agree. Recorded as 3/3.
p3.4G, G, RGTwo of three. Recorded as 2/3, so a reviewer can see it was a closer call.
an unseen unitX, D, RXNo majority. The category earliest in X, G, D, S, E, C, R, B wins.

Why break ties by precedence: a missed fact costs the bid manager more than an extra one, and X (disqualification) and G (gate) are the costliest to miss. Model flags (post-award, risk, unclear) are kept only if most of the agreeing runs set them.

4. Build the facts

A coded unit starts a fact. A = unit within 3 units of the last attached unit joins it. A - unit makes nothing. Applied to the excerpt, p3.1 makes nothing, p3.2, p3.3 and p3.6 each start a fact, and p3.5 joins p3.4:

Which text is shown: the statement or the RFP's words

Code compares every number and date in the model's statement with the cited text. If all appear, the statement is shown. If one does not, the RFP's own words are shown instead.

Statement passes
Statement: Proposals due: 2026-08-28 16:00
Source:    ...4:00 p.m. on August 28, 2026.
Shown:     the statement
Statement fails
Statement: Proposals due: 2026-08-29 16:00
Source:    ...4:00 p.m. on August 28, 2026.
Shown:     Proposals are due by 4:00 p.m.
           on August 28, 2026.

Why: a wrong figure is never shown as the RFP's. The fact ID comes from the first unit, so it survives changes to the wording, the category or the run.

5. Add contradictions (Q facts)

Amber: a model call. Teal: ordinary code. Two finders feed Q facts; if both report the same cited units they merge into one Q fact. The code check only catches reference mismatches. Every other kind of contradiction comes from the CHECK call.

6. Second round, without the PDF (GROUP and BRIEF)

These calls see only the finished facts, never the document, so they are small and fast. They never remove or change a fact. They only add structure around the facts. Two kinds run at the same time: GROUP, one call per category, and BRIEF, one call per summary section.

GROUP: tidy repeats and lists, one call per category

A category is only sent if it has at least 4 facts. The model sees numbered lines of number|page|fact and answers with groups of line numbers:

If a SAME group’s members hold different numbers or dates, code downgrades it to a list titled “Related statements”, so nothing hides behind another fact.

The number check on every row

Code marks a row checked only if it cites at least one fact and every number and date in its text appears in the cited facts or their source text. A row that fails is not trusted: the screen shows the cited facts themselves instead of the model’s sentence.

The five summaries are saved in the run report and appear on the Overview page. The web workspace also has its own, separate summaries (seven sections, such as Key dates and Requirements). Those are written by the web layer from the facts as you correct them and are not part of this phase.

7. Return

The caller gets the facts, a label for every unit (so you can audit the units that made no fact), and a report. For the excerpt it would read:

ids 6 | facts 4 | by_category  D 1, X 1, G 1, S 1
units_coded 4 | units_continuing 1 | units_without_a_point 1
facts_votes_agreed 3 | facts_votes_split 1
facts_with_statement 4 | facts_in_rfp_words 0
failed_calls []  incomplete_calls []  cut_calls []

The report also holds timings, token use, the cache hit rate for calls 2 to N, and a record of every call, so a reviewer can tell a thin result from a complete one.

Why it is built this way

The model does not write the list

Asking for "the facts" gives a different list each time and can invent items. A closed question per unit means every fact is a real sentence, and code fixes the set of candidates.

Three votes

One labelling is unstable: two runs still differ on about one unit in ten. Votes smooth that out and the 2/3 record shows which facts were close calls.

Wording is asked separately

The statement call cannot influence the category, and a bad statement cannot change which facts exist.

Numbers checked in code

If a statement has a number or date not in the cited text, the fact shows the RFP's own words. A wrong figure is never shown as the RFP's.

Results are stored

Runs are not perfectly repeatable, so a finished result is saved under the PDF's content hash and shown again. Changing prompts or unit cutting bumps the pipeline version (units-4 now).

When a model call goes wrong

ProblemWhat happens
Rate limitWait and retry with growing delays, up to 5 times.
Error or 120 s timeoutRetry once. If it fails again the call is marked failed: its units have one vote fewer, or no statement, so those facts show the RFP's words.
Answer skips unitsThe call is sent once more and the fuller answer is kept. Still short: marked incomplete.
Output cut at the length limitLines already written are kept; the call is marked partial.

All of these are listed in the run report, so a reviewer can tell a thin result from a complete one.
