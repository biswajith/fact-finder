ingest_document: one call that takes a document into a bid

A document comes into a bid that already has facts: an addendum, a Q&A, a reissued RFP, a call, deal notes. One operation reads it, votes, compares it with what the bid already says, updates the fact list, and returns what changed. inject_addendum is this operation with the change-addendum playbook.

Status: proposal. Nothing built yet. Used by the agent (as a tool) and by the UI (as an API), both over one Python function.

What already exists

Most of the work is already in the bid pipeline. It is spread over three or four calls, the orchestration lives inside the web server, and nothing reports the result as a change.

the one step that waits on a person

  • Step 2 is a gate, not a pause in the middle. If the playbook, issue date, number, speakers or previous version is missing, the call returns what is missing and spends no tokens. Once the gate passes, steps 3 to 7 run without stopping.
  • Step 5 also re-relates documents that came in out of order. If addendum 3 was loaded before addendum 2, the ladder still applies them in issue order, so the report can include facts from documents other than the one just added.
  • Step 7 is pure code. It compares the state from step 3 with the state after step 6. It makes no model calls.

"Update existing facts" means supersede, not rewrite

The ladder never changes a fact's text. An addendum that moves the due date adds a new fact and marks the old one replaced_by it. The user can undo that by rejecting the relation (/api/relations/{rid}/reject). This is what makes it safe to run the skill without someone watching every step, so it must stay.

What a document is allowed to do depends on its level, which comes from the playbook:

PlaybookLevelCompare byEffect on existing facts
change-addendum1RELATE, all seven kindsLater issue replaces or removes, unless the confirmed order of precedence says otherwise
qa-addendum1RELATE, all seven kindsSame as above. Answers mostly CLARIFY, but an answer can still replace a value.
reissued-rfp1Text alignment with the previous versionAligned facts carry over with the user's corrections; the rest are new or removed

deal-notes4RELATE: confirms, clarifies, disagrees, addsNever replaces. A disagreement becomes a conflict for the user.

Where playbooks fit

A playbook is the parameter

It says how to read one kind of document: its codes, flags, the calls to run, the relation kinds, the level and the votes. It doesn't change.

The skill is the orchestration

It says what to do to the bid when a document arrives. One skill covers every document type because the playbook supplies everything specific to the type.

So there is no separate inject_addendum, inject_transcript and so on. There is ingest_document(…, playbook=None), and the classifier picks the playbook when you don't give one. Keep the order of steps in code. If a later document type needs different steps after extraction, add a header key such as after: then, not now.

Build order

  1. Move the orchestration out of the server. Move bid_work.go() into ingest.py and have the server call it. No change in behaviour; the existing bid e2e tests must still pass.
  2. Add the snapshot, the diff and what_changed. Test with the scripted client on a base RFP plus one change addendum, including one that arrives out of issue order.
  3. Add the REST routes and the report field on the job.
  4. Add the agent tools and the confirmation rule for ingest_document.
  5. Add a change-report panel in the UI after a run. changesView.ts already has wordDiff for old-versus-new fact text.

Open questions

  • Fact ID stability. The diff assumes bid.build keeps an existing fact's ID when nothing about it changed. Check this before step 2 of the build. If IDs move, diff by source unit instead.
  • Preview before applying. Should the agent be able to show the report before the ladder applies it? Today relations are applied and then reversible one by one. A preview would need the ladder to run on a copy, which is cheap because the ladder is pure code.
  • Files in chat. The agent has no way to receive a file today. prepare_document needs the chat to accept an attachment and hand over its upload ID.
  • Cost. Show an estimate of the model calls at the confirmation step: units × votes × calls, plus RELATE batches.
  • One job at a time. The server refuses a second extraction while one runs. Two addenda dropped together should queue as one job in issue order, not fail.
